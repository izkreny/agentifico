# The reviewer model

**Read this file before the spawn at Step 1 of `workflows/review.md` whenever the repository's config file carries a `Reviewer model:` line**, per the per-repo config convention in `SKILL.md`. It owns what the line changes about the spawn, and why an unaccepted model refuses the round rather than falling back.

## The model a round asks for is a per-repo fact

The reviewer is always the `reviewer` agent this plugin ships. The repository's config, found by the lookup `references/repo-config.md` owns, may name the model a round asks it for.

- **Read `Reviewer model:` and pass it on the spawn.** Where the repository's config file carries that line, it names the model this round asks the spawn for; absent it, the spawn asks for nothing and the agent's own frontmatter decides. **Validate the value against the names the spawn parameter accepts, and against the effort the agent's frontmatter pins** - the spawn parameter is the authority on the set of names and the model is the authority on which effort levels it offers, so read both there rather than matching a list written here, which would date the moment model ids move. A named model that does not offer the pinned level is a pair the harness will not honour, and spawning it produces a review whose depth silently differs from the one declared. **Either failure refuses the round**: `⛔ REFUSED - {value} is not a model the spawn accepts`, or `⛔ REFUSED - {value} does not offer the effort the reviewer pins`. Never fall back to the session's model: the owner would believe they are comparing rounds run on the model they named.
- **The model is a spawn parameter, not context.** It travels beside the PR number rather than in the prompt, so it takes nothing away from the reviewer fetching its own context.
- **Name the model the round asked for in the round report**, always, including when it is the default. A round's findings mean something different depending on what produced them, and a report that leaves the model out cannot be compared with another round's. **The request is the outcome**: a model asked for at spawn time outranks `CLAUDE_CODE_SUBAGENT_MODEL`, which the documentation makes a default rather than an override unless `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` is set, so the report names the model asked for as the model that ran, that variable aside. **The effort is reported as a request**, because the documentation has `CLAUDE_CODE_EFFORT_LEVEL` outrank the `effort` the agent's frontmatter pins.
